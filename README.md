# Борей-89 · статическое расширение Owlbear Rodeo 2.0

Личные дела в стиле советского НИИ 1989 года: Охранник, Медик, Электрик и Механик. Сохранены бумажные карточки, вкладки, здоровье, стресс, симптомы, инвентарь, ФИО, записи, задачи и сброс листа. Кнопка расширения открывает popover; «Окно» — модальное окно внутри Owlbear. Интерфейс адаптируется к узкой панели.

**Свой сервер, SQLite, коды доступа и авторизация не нужны.** На GitHub Pages публикуется только содержимое `dist`. Node.js используется для разработки, сборки и тестов, а не для обслуживания игры.

## Как пользоваться

1. Добавьте расширение в Owlbear по инструкции ниже и включите его в комнате.
2. Откройте кнопку «Борей-89 · Личное дело» и выберите профессию. У каждого пользователя Owlbear четыре независимых листа — по одному на профессию. Два игрока могут выбрать одну профессию, не перезаписывая друг друга.
3. Меняйте показатели и поля. Через 350 мс после последнего изменения начинается сохранение через `OBR.room.setMetadata`. Дождитесь **«Сохранено в комнате Owlbear»** перед закрытием листа. При повторном открытии выберите нужную профессию: её данные загрузятся из комнаты, а не из браузерного кеша.
4. Ведущий получает список игроков, которые уже сохранили хотя бы один лист. В поле «Лист игрока» он выбирает участника, затем профессию. Правки ведущего и игрока синхронизируются через `OBR.room.onMetadataChange`, без опроса собственного сервера. Новые пустые листы появляются в метаданных только после первого изменения.

Листы привязаны к ID пользователя и комнате Owlbear; другая комната или другая учётная запись имеют отдельные данные. Сохранение не зависит от выбранной сцены. Оно доступно, пока существует комната и её метаданные не удалены. Смена имени пользователя не меняет ID листов.

**Все данные листов общие для участников комнаты.** Переключатель ведущего — удобство интерфейса, не граница безопасности. Никакой серверной проверки владельца или запрета чтения чужого листа здесь нет. Личные тайны, холод, заражение и галлюцинации удалены из интерфейса и формата данных; ведущий ведёт их вне расширения. Не пишите секреты в заметках, задачах или ФИО. Надпись «Конфиденциально» — часть исходного дизайна, не обещание приватности. Подробнее: [SECURITY.md](SECURITY.md).

## Бесплатная публикация на GitHub Pages

Для GitHub Free используйте **публичный репозиторий**. Хостинг приложения, базы данных и платные сервисы не нужны; сохраняемые игровые данные находятся в Owlbear, а не в GitHub.

1. Слейте Pull Request этой версии в `main`.
2. Откройте репозиторий **Settings → Pages → Build and deployment → Source → GitHub Actions**. Разрешите Actions, если они отключены в настройках репозитория.
3. В разделе **Actions** дождитесь успешного workflow **Test and deploy to GitHub Pages**. Если слияние произошло до включения Pages, запустите workflow вручную через **Run workflow**, выбрав `main`.
4. Workflow устанавливает зависимости, выполняет тесты, собирает фронтенд, запускает Chromium-тесты, загружает `dist` и публикует Pages. Последующие push/merge в `main` публикуются автоматически. Pull Request проходит проверки без публикации.
5. Адрес для этого репозитория после успешного deploy:

   ```text
   https://zedroma80-debug.github.io/borey-89/
   ```

   Манифест расширения:

   ```text
   https://zedroma80-debug.github.io/borey-89/manifest.json
   ```

   Это **целевые адреса**, не утверждение, что публикация уже выполнена. Окончательный URL также показывается в Settings → Pages и результате deploy.

Workflow использует стандартный `GITHUB_TOKEN`, без пользовательских токенов и секретов. Права публикации `pages: write` и `id-token: write` выданы только deploy-job. На `main` отправляет изменения пользователь после просмотра PR; ветка разработки автоматически не публикуется.

## Установка в Owlbear Rodeo

1. После успешной публикации откройте URL манифеста и проверьте, что он возвращает JSON, а не страницу 404. Поля `action.popover` и `icon` должны содержать `/borey-89/`.
2. В управлении расширениями аккаунта Owlbear Rodeo выберите добавление расширения по URL и вставьте **полный URL `manifest.json`** выше. Версия манифеста — `manifest_version: 1`: это актуальный формат расширений для Owlbear 2.0.
3. Включите добавленное расширение в нужной комнате через управление расширениями комнаты. Участники используют один размещённый URL.
4. Нажмите кнопку «Борей-89 · Личное дело», выберите профессию и проверьте сохранение. «Окно» открывает лист внутри Owlbear, без перехода на сайт.
5. При обновлении обновите расширение в управлении Owlbear и заново откройте лист. Ведущему и игрокам рекомендуется использовать одну версию.

Если при прямом открытии Pages отображается «ЛОКАЛЬНАЯ ПРОБА», это ожидаемо: SDK доступен только внутри Owlbear. Проба сохраняется в localStorage этого браузера, не синхронизируется с комнатой и автоматически в неё не переносится.

## Локальная разработка и проверки

Требуются Node.js 24 и npm. Команды выполняются из корня репозитория:

```sh
npm ci
npm run dev
```

Vite обслуживает приложение по пути `/borey-89/` на порту 5173. Для проверки готовой статической сборки:

```sh
npm run build
npm run preview
```

`dist` содержит готовый HTML, CSS, JS, иконку и манифест. Бэкенда и `/api` нет. Не открывайте `index.html` напрямую через `file://` — используйте HTTP-сервер для локальной проверки.

```sh
npm test
npm run build
npx playwright install chromium
npm run test:ui
```

Если Chromium уже установлен, можно использовать `CHROMIUM_PATH=/usr/bin/chromium npm run test:ui`. Тесты проверяют сохранение разных игроков/профессий, подписки и конфликты, отсутствие секретных полей, вкладки, счётчики, симптомы, инвентарь, ФИО, записи, задачи, перезагрузку, ширину 360 px и манифест/модальное окно по пути GitHub Pages. Браузерный стенд использует настоящий SDK и его postMessage-протокол с тестовым родителем; **живую комнату Owlbear он не заменяет**.

Перед первой игрой проверьте в настоящей комнате с отдельными аккаунтами: сохранение после закрытия листа, одинаковую профессию у двух игроков, просмотр/правку листа ведущим и работу отдельного окна.

## Путь размещения

По умолчанию `BASE_PATH=/borey-89/`. Vite корректирует адреса ассетов и собранного манифеста; SDK-модальное окно использует тот же base path. Workflow автоматически берёт имя репозитория для этого пути.

Для другого пути или собственного домена передайте путь **при сборке и тестировании**:

```sh
BASE_PATH=/ npm run build
BASE_PATH=/ npm run preview
BASE_PATH=/ npm run test:ui
```

При собственном домене с корнем `/` измените `BASE_PATH` в workflow на `/`. Не редактируйте вручную хешированные файлы `dist`. Файл `public/manifest.json` содержит адреса стандартного `/borey-89/`; сборка генерирует итоговые значения для `BASE_PATH`.

## Сохранение и конфликты

Каждый лист записывается отдельным namespaced-ключом метаданных `com.borey89.characters/v2/<ID игрока>/<профессия>`. Чужие ключи, другие профессии и настройки других расширений не заменяются. Пустые листы не записываются автоматически. Ограничения: 40 предметов, 90 символов на предмет, 200 символов ФИО, 2000 символов записей, 1500 символов задач и 12 КБ UTF-8 на запись. Дополнительные лимиты Owlbear могут ограничивать суммарный объём метаданных; ошибка SDK показывается пользователю, без сообщения об успешном сохранении.

Перед записью сверяется версия листа, после записи проверяется результат, а чужие правки во время ввода вызывают предупреждение. Но **SDK не предоставляет compare-and-swap/блокировку**: при строго одновременной записи в один лист возможна последняя победившая запись. Избегайте параллельного редактирования одного персонажа. Разные игроки и профессии пишутся в отдельные ключи.

При ошибке или обнаруженном конфликте черновик остаётся в открытом окне. «Скачать несохранённый лист» выгружает JSON; «Загрузить сохранённую версию» заменяет черновик данными комнаты после подтверждения; «Повторить сохранение» полезно после восстановления связи или сокращения слишком большого текста. Для конфликта сначала сохраните черновик, загрузите общую версию и перенесите нужные изменения вручную. Автоматического импорта JSON нет. Если закрыть окно до успешного сохранения, несохранённые правки могут потеряться.

Старые SQLite-файлы, browser storage и тайны предыдущей серверной версии **не импортируются** в общие метаданные. Если нужны прежние обычные записи, перенесите их вручную после удаления секретной информации. Локальные старые БД остаются вне Git и не нужны для сборки.
